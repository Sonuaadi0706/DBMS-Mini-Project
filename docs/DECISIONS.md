# Design decisions

Every `[ASSUMED]` choice from the spec and every deviation from it is recorded here.

| # | Decision | Why |
|---|---|---|
| D-01 | Native Homebrew PostgreSQL 18 + pgvector and MongoDB 7 are used for development; `docker-compose.yml` is kept as an optional path. | Docker is not installed on the dev machine. The spec targets PG 16; nothing used is version-specific (identity columns, partial indexes, `FILTER`, procedures, HNSW all exist in 16). |
| D-02 | Migration files contain no `BEGIN/COMMIT`; `scripts/migrate.ts` wraps each file and its `schema_migrations` row in one transaction. | Spec §8.3 asks for each migration to be atomic and self-recording. Doing it in the runner keeps the files short and guarantees both happen together. |
| D-03 | `scripts/migrate.ts` creates the target database if it does not exist, and creates `projectpulse.schema_migrations` before running 001. | One-command setup; the runner needs the bookkeeping table before 001 can be recorded. |
| D-04 | Migration 013 is skipped (with a warning, not recorded) when `APP_DB_PASSWORD` is not set. | Spec §8.13 allows skipping it on demo machines where it causes trouble. The password is substituted by the runner, never hard-coded. |
| D-05 | The `git_activity` evidence cap (5 per member per milestone, spec 9.4) is **not enforced** in version 1. `git_activities` has no milestone column, and manual commit references are unverified until the guide checks them, so they carry no weight on their own. | A counting policy, not an integrity rule; the seeded data has at most 3 commits per member. Revisit if commit spam becomes a problem. |
| D-06 | Full-text query Q12 uses the same expression as the GIN index (title + abstract + problem statement) so the index is usable. | An expression index is only used when the query expression matches it exactly. |
| D-07 | Migration 012 (DROP demo) creates then drops a temporary index, view and column. | Demonstrates DROP INDEX / VIEW / COLUMN as the proposal requires. Safe: nothing depends on them, and they never existed outside that migration. |
| D-08 | The seed (`db/seeds/scenarios.ts`) drives data through the real triggers (transition guard, audit, evidence, overdue flags). Only afterwards `backdateHistory` rewrites timestamps, with `trg_tasks_updated` disabled for that single statement. | Spec 9.3 prefers exercising the triggers. Backdating is needed because the risk function reads `updated_at`, which the trigger would otherwise reset to now(), making the "inactive for 11+ days" scenario impossible. Statuses are never rewritten. |
| D-09 | Seed scenario lengths: Delta starts 80 days before today so its M4 (test report missing) falls within the 7-day look-ahead of the missing-deliverable rule; Bravo starts 47 days ago so M2 is ~12 days overdue. | Keeps each scenario's expected risk level (Bravo high, Charlie/Delta moderate, Alpha low) deterministic whenever the demo is run. Delta sits just above the 25-point moderate boundary (25.06); changing its feedback or deliverable data can drop it to low. |
| D-10 | Seeded MongoDB documents/threads/meeting notes, embeddings and `similarity_reviews` are not part of `npm run db:seed`. | They belong to the Mongo and pgvector slices (`mongo:init`, `embed:backfill`). The SQL side already holds the matching `deliverables` and `feedback_items` they will reference. |

| D-11 | Access is decided by the user's **relationship to the project** (team member, allocated guide/reviewer, admin), loaded from the database on every request (`src/lib/auth/access.ts`), not by the role in the JWT. Non-participants get 404, not 403. | A user can hold several roles; relationship is what grants access, and 404 avoids revealing that another team's project exists (hard rule 4a / T-05). |
| D-12 | The API decides **who** may trigger a transition (students move tasks forward, only the guide verifies or approves); the database decides whether the transition itself is legal (`status_transitions` trigger). | Matches spec 9.7. Illegal jumps such as `todo -> done` are refused by the DB even if the API check is bypassed. |
| D-13 | Re-applying the same status (e.g. starting an already started milestone) is an idempotent no-op. | The transition guard only fires when the value actually changes; treating a repeat click as success is harmless. |
| D-14 | `POST /api/milestones/:id/decision` also writes the guide's `reviews` row (updating a pending one or inserting a new one) and accepts submitted deliverables on approval. | Keeps the milestone status and review history consistent in one transaction until the full review/feedback slice. |
| D-15 | Milestone **submission** (the atomic multi-table transaction, spec 9.5) is intentionally not part of this slice; it ships with deliverables on day 4. Until then the UI tells the team where submission will live. | Submission needs deliverables, versions and the MongoDB document; building half of it would hide the transaction the spec wants demonstrated. |
| D-16 | The first planning action (apply template / add milestone / start milestone) moves an `approved` project to `in_progress`. | `approved -> in_progress` is a legal transition and gives the project a natural start event. |
| D-17 | `ON DELETE RESTRICT` raises SQLSTATE `23001` (not `23503`); the API error mapper handles both. Friendly texts for named unique indexes live in `CONSTRAINT_MESSAGES`. | Discovered while writing the DB tests. |
| D-18 | Seeded MongoDB data (documents, feedback threads, meeting notes) is now part of `npm run db:seed` and re-created on every seed. Every seeded document version has a real tiny `.md` file under `storage/uploads/seed/` so downloads and text extraction work. | Supersedes D-10. MongoDB is populated from the committed PostgreSQL rows, so ids always match. If MongoDB is down the SQL seed still succeeds with a warning. |
| D-19 | A returned deliverable is one the guide explicitly rejects. Requesting a milestone revision does **not** reject the other submitted deliverables. Uploading a new version to a returned deliverable moves it back to `draft`; resubmitting the milestone submits all drafts. | Keeps the guide in control of exactly what must be reworked and avoids forcing re-uploads of work that was fine. |
| D-20 | The atomic submission test hook is `x-test-fail-at: N`, honoured only when `ENABLE_TEST_HOOKS=1` and `NODE_ENV` is not `production` (the spec said `NODE_ENV=test`). | `next dev` always runs with NODE_ENV=development, so a NODE_ENV=test switch could not be used against a real running server. |
| D-21 | `file_size_bytes` of an externally linked file is deliberately NOT range-checked by the API. The database CHECK rejects a negative value at step 3 of the submission and the whole transaction rolls back. | This is the spec's required rollback demonstration (T-15); the database stays the authority on validity. |
| D-22 | Uploads: extension allow-list (pdf, docx, md, txt, png, jpg, zip), max `STORAGE_MAX_FILE_MB`, content check (magic bytes / no NUL in text), random storage names under `storage/uploads/`, SHA-256 stored, served only through `/api/files/:versionId` with `attachment` + `nosniff`. Next.js only gives middleware the first 10 MB of a body, so `middlewareClientMaxBodySize` is raised to max file size + 2 MB and oversized uploads are refused with 413/422 instead of arriving truncated. | Spec section 16, plus a bug found by the oversized-upload test. |
| D-23 | New versions of an existing deliverable are appended to the MongoDB document after the SQL commit (best effort); `npm run mongo:reconcile` rebuilds `versions[]` from PostgreSQL and deletes `pending` documents older than one hour. Creating a deliverable and the milestone submission use the strict pending-then-confirm flow. | The spec's compensation rule is applied where a new document is created; for appends a repairable derived copy is simpler than a per-version pending flag. |
| D-24 | Students see only feedback **assigned to them** and only their **own** evidence (permission matrix 4.1); the guide, reviewers and admin see the whole project. A teammate who is not the assignee gets 404. | Follows the matrix literally; stricter than "own team". |
| D-25 | Reviews: the reviewer owns their rubric and comments (`PATCH /api/reviews/:id`, total derived from the rubric). The **guide's** final decision goes through the milestone decision endpoint so the milestone and the review never disagree. A non-guide reviewer records a recommendation on their own review. | Avoids two ways to decide the same thing. |
| D-26 | Test runs are ordered (database tests, read-only API tests, then mutating tests) by `tests/sequencer.mts`, and when `ALLOW_MUTATING_TESTS=1` the demo is restored automatically at the end (`tests/globalSetup.ts`). The config files are `.mts` because `vitest/node` is ESM-only. | The mutating tests intentionally change the data the seed regression tests expect. |
| D-27 | Risk is recalculated three ways: the guide/admin **Recalculate** button and the **sweep** always store a new snapshot (`sp_recalculate_risk`); **automatic refresh** after key events (milestone start/submit/decision/plan changes, task status, feedback actions, evidence verification) stores one only when the score or reason actually changed. | The history and trend then show real changes instead of one row per click. |
| D-28 | `POST /api/jobs/risk-sweep` is reachable without a session (the middleware lets it through) and authorises itself: a constant-time match of the `x-job-secret` header against `JOB_SECRET`, or an admin session. The terminal script `npm run risk:sweep` does the same work with a progress bar. | Spec 5.8 RISK-04: no external cron needed, but a scheduler can call it. |
| D-29 | Risk visibility follows the permission matrix: the team sees level, score and the plain-English reasons; the guide, reviewers and admin also see the six-factor breakdown, trend, risk events and history. The formula is shown to everyone under "How is this calculated?". | Explainable for everyone, detailed monitoring for staff. |
| D-30 | Reports are scoped in SQL (admin: all; guide/reviewer: allocated projects only), filtered by bound parameters, and sorted through a fixed whitelist of expressions, so a hostile `sort` value is ignored. "More than N overdue tasks" is a strict `HAVING COUNT(*) > N` as in Q2. CSV cells starting with `= + - @` are prefixed with `'` to block spreadsheet formula injection. | Spec 10.2 and 16 (SQL injection), plus a standard CSV-export safeguard. |
| D-31 | The dashboard shows the dashboard of the **active role** (role switcher). A guide dashboard covers projects where the user is the *guide*; being a *reviewer* is shown on the reviewer dashboard. | A multi-role user (guide3) sees each responsibility separately. |
| D-32 | A student sees only their own contribution row (indicator, points, verified/waiting counts, anonymised average peer score). Peer-evaluation entry screens are left for the P1 slice (the seeded peer scores already feed the indicator). | CON-04. |
| D-33 | Similarity compares sections like-for-like (title with title, abstract with abstract ...) rather than every chunk with every chunk, and the project score is the weighted mean of the best section similarities over the sections both proposals have. | Matches the section weights of the spec and keeps the SQL simple. Section weights, threshold (0.80), single-section limit (0.90) and top-k (5) are in `src/lib/embeddings/scoring.ts` / `.env`. |
| D-34 | The seeded near-duplicate (Echo vs Alpha) uses a close paraphrase. The first wording scored only 0.69 with the real model, below the 0.80 threshold, so the text was changed, not the threshold or the score. | Spec 12.2 asks for a clearly overlapping pair; the numbers shown are always the model's real output. |
| D-35 | `npm run db:seed` also embeds the proposals and screens them (needs the model, ~25 MB, downloaded on first use). `SEED_EMBEDDINGS=0` skips it; `npm run embed:backfill` repeats it any time. If the model cannot be downloaded the seed still succeeds with a warning. | One command gives the complete demo; the SQL and Mongo parts never depend on internet. |
| D-36 | With the tiny demo data PostgreSQL prefers the small filter index to HNSW for a filtered nearest-neighbour query. Tests therefore prove (a) an unfiltered query uses `idx_embeddings_hnsw` and (b) the filtered query returns exactly what a full scan returns; `docs/EXPLAIN_ANALYZE.md` shows the HNSW effect on 6,000 synthetic vectors inside a rolled-back transaction. | Honest evidence: the planner is right for 30 rows and the index is right for thousands. |
| D-37 | Embedding happens after the SQL commit of a submission; if it fails the submission stays valid and `npm run embed:backfill` can repair it. A rejected proposal's vectors are set `is_current = false`. | A model or download problem must never block a student from submitting. |
| D-38 | Administration (users, roles, departments, courses, templates, allocations, audit) lives under `/admin/*` for admins only. A role that is still in use cannot be removed (a student in a team, a guide allocated to a project, the last role of a user, one's own admin role); suspending an account takes effect immediately; editing a template never changes running projects (applying a template copies it). | ADM-01 / AUTH-06. |
| D-39 | Peer evaluation: one rating per teammate per milestone (the evaluation period; the unique key would not stop duplicates for a NULL milestone, so the API requires one). Staff see who rated whom; students see only an anonymous average and comments about themselves. | CON-03 and the anonymity rule of the permission matrix. |
| D-40 | Progress bars print line by line when the output is not a terminal and `FORCE_PROGRESS=1` is set (used to capture the report screenshots); in a normal terminal nothing changes. | cli-progress hides itself without a TTY. |
| D-41 | The report (`report.pdf`) is built by `npm run docs:report`: Markdown (`docs/REPORT.md`) with live directives (queries, aggregations, code excerpts, counts) -> HTML -> the installed Chrome prints the PDF; diagrams use Mermaid. Screenshots come from `npm run docs:screenshots`. | pandoc / mmdc are not installed; building from live data keeps every number in the report true. |
| D-42 | Not built (optional P2 items): in-app notifications (table exists), rate limiting on login / similarity, a strict Content-Security-Policy, Playwright end-to-end tests, per-section embeddings of uploaded document text. Cut in the order the specification gives for a tight schedule. | Documented as future work in the report. |
| D-43 | The interface is deliberately calm and flat: neutral graphite (dark, the default) or paper (light), solid surfaces with hairline borders, one teal accent, one typeface (Inter) and short fade transitions. The heartbeat line that follows the risk level is the only decorative motif (login, page headers, risk page). Colours are CSS variables in `src/app/theme.css`; Tailwind's colour scales read them, so every page follows the theme. Animations respect `prefers-reduced-motion`. | An earlier glass-and-glow version was replaced because it looked busy and the sidebar did not match the content. Presentation only; no database or API change. Fonts come from `next/font/google`, so the first `next dev` or `next build` needs internet. |
| D-44 | No `loading.tsx` under `(app)`. A loading boundary streams the page shell before the page runs, so a forbidden page would answer 200 instead of 404 and the access tests (and any client relying on the status) would be misled. | Correct status codes matter more than a skeleton. |
